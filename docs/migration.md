# Переход к общему рабочему исходнику

Старые версии доступны через Git-историю и прежние теги. Исполняемые FF,
board-only, offline-finalizer и Windows wrappers удалены из актуального дерева.
Исторические evidence не становятся доказательствами нового запуска.

Перед переносом сохраняются Git refs, незакоммиченные файлы и точная выборка
установленного потребителя. Подключение исходника проверяет хеши предшественника
и удерживает локальную delivery.lock. Прежние receipts сохраняются.

Есть два способа использовать один код: установленная runtime-копия и ссылки
на общий checkout. Разработчик может подключить также тесты. Обычному потребителю
тесты и их запуск в CI не нужны. Shared checkout может находиться по любому пути.

Board, openspec/changes, профиль, проектный launcher и runtime не становятся
общими. Git-операции доставки выполняются в репозитории потребителя. Правка
через ссылку принадлежит Git-репозиторию ChangeRail; status потребителя не
показывает содержимое изменённой цели ссылки.

Новые процессы видят исправление сразу. Старые процессы продолжают исполнять уже
загруженный Python-код; автоматическая остановка на границе этапа не гарантируется.
Перед изменением общего исходника оператор останавливает runner во всех подключённых
проектах и проверяет завершение дочерних процессов. Изменение process identity
блокирует обычный `resume`. Узкий [Python repair](runtime-repair.md) с регрессией
доступен лишь до первого принятого checkpoint и evidence первичного native run
с общим исходником; для поздних этапов и исторических runs такого перехода нет.
Не меняйте старые `run.json` и не переносите старое GO на новый код молча.
Порядок диагностики — в [руководстве оператора](operations.md).

Прерванный archive сохраняет исходный `native-archive-intent.json`. Если stock
OpenSpec ещё не переместил change, а дата UTC уже сменилась, продолжение сначала
проверяет прежний HEAD, точные байты артефактов, остальные изменения и отсутствие
обоих архивных каталогов. Затем оно добавляет датированный successor intent
в `native-archive-intent-successors/`, связанный хешем с предшественником,
и вызывает штатный archive. Исходный intent остаётся неизменным; цепочка
наследуется следующим запуском. Уже выполненное точное перемещение подтверждается
по сохранённому назначению, независимо от текущей даты. Коллизии и изменения
payload останавливают продолжение; review и evidence accounting не обнуляются.

Если дата меняется внутри уже выполняющегося stock archive, этот механизм
не выбирает другое назначение автоматически: команда останавливается с ошибкой.
Описанное продолжение покрывает сохранённый intent до начала перемещения.

## Потребитель со старыми symlink-обёртками

Установка поверх старого подключения 0.x — не новая пустая установка.
Сначала проверьте `git status`, тип каждого legacy entry (`lstat`/`readlink`),
старый consumer lock и сохранённые runs. Новый installer/attach-inventory
отклоняет symlink, в том числе `bin/openspec`, даже если он указывает на тот же
доверенный checkout. Это ожидаемая граница; `--adoption` не разрешает ссылки.

Перед изменениями остановите затронутые процессы и сохраните в закрытом
игнорируемом каталоге Git HEAD/index/diff, локальные настройки, старый lock,
сами ссылки без разыменования и runtime history. Составьте точный список
принадлежащих старому инструменту путей с типом, literal target для ссылок,
хешем и режимом для обычных файлов. Не используйте массовое удаление `.codex`,
`.claude`, `bin` или `scripts`: там остаются проектный launcher, domain skills,
provider config и продуктовые файлы.

После проверки списка перенесите **только его entries** в сохранённый backup
без перехода по ссылкам. Старые FF/do helpers, compatibility prompts, generic
lifecycle links и consumer lock не должны оставаться активными рядом с native
маршрутом. Не удаляйте цели ссылок в общем checkout. Для оставшихся обычных
predecessor-файлов используйте штатный `inventory --paths-file` и hash-bound
adoption. Затем повторите `install --dry-run` и `install` опубликованного архива
или `attach-inventory`/`attach` для выбранного режима. Backup и описание переноса
сохраняются у потребителя; новый distribution lock не описывает этот предыдущий
ручной переход. При его сбое восстанавливается проверенный список из backup,
без переписывания исходных receipts и без удаления audit ради повтора.

## Существующая OpenSpec-история и проектные инструкции

Если у потребителя уже есть архивы старого lifecycle, новый `wiring` без
явного history manifest может отклонить их как `unowned addition`.
`--retain-history-read-only` в установщике фиксирует сохранённые **run.json**;
это не снимок старых файлов `openspec/changes/` и не замена проектному manifest.

В локальном профиле выберите проектный документ, например:

```toml
[history]
manifest = ".changerail/history.json"
```

Документ имеет schema `changerail.project-history.v1`, поле `files` с
отображением относительных путей старых файлов `openspec/changes/` в SHA-256
и `board_records` (может быть пустым объектом). Снимок создают из отдельно
проверенной исторической выборки **до** добавления новых native changes;
активные изменения сначала разбирают явно. После фиксации нельзя обновлять хеши
ради обхода ошибки: новый runtime проверяет неизменность истории. Исторические
карточки не получают права исполнения; новые используют `openspec-v1`.

Обновите инструкции потребителя и шаблон карточки под одну карточку/один change,
два независимых ревью, `native-accept`, `doctor`, `run` и `resume`. Если родительский
репозиторий ещё описывает FF/do, локальные инструкции должны явно заменять этот
маршрут для мигрированного компонента. Не переносите продуктовую политику в defaults
ChangeRail. Сохраните отдельные изменения пользователя: успешный `wiring` не
отменяет требование чистого рабочего дерева для начала доставки.
