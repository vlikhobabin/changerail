# ChangeRail 2.0.0-rc.6

Кандидат предварительного выпуска линии 2.0.0. Планируемый тег — `v2.0.0-rc.6`,
Python metadata — `2.0.0rc6`. Подготовка этих notes не означает завершения CI,
публикации или переключения локальных executors.

## Выход из двух подряд NO-GO

Два подряд независимых NO-GO больше не тупик и не путь ошибки. После **каждого**
NO-GO runner строит детерминированный разбор повторяемости по сохранённым
вердиктам всей линии восстановления: какие условия провалены повторно, какие
закрыты, какие провалены впервые, какие findings ссылаются на уже названные пути.
Разбор не меняет вердикты, план и карточку и попадает в контекст следующего
ремонта, поэтому ремонт видит историю, а не только последний список findings.

При исчерпании общего остатка появляется ограниченная диагностика: класс из
закрытого набора (`repeat_defect`, `incomplete_work`, `plan_conflict`,
`evidence_model_gap`, `unreproducible`, `infrastructure`, `unsatisfiable`),
обоснование, варианты с эффектом, ценой, предусловиями и рекомендацией. Разбор
идемпотентен и привязан к точному состоянию линии: в его digest входят история
ревью, принятый план и payload, поэтому изменение байтов делает прежний разбор и
записанное решение неприменимыми. Если в профиле задан необязательный route
`[models.diagnosis]`, неопределённая ситуация уточняется одной ограниченной
сессией; класс, отрицающий наблюдаемое, отклоняется runtime.

## Штатная остановка и операторский выбор

Исчерпание останавливает run кодом `3` в состоянии
`awaiting-operator-decision` с сохранением истории, accounting и frozen identity;
`status` показывает `stop_state` и `awaiting_decision`. Выбор оператора
фиксируется неизменяемой записью, связанной с точным разбором: тот же выбор по
той же причине идемпотентен, та же причина не может нести другой переход, а
пересмотренное решение записывается со своей причиной и ведёт продолжение.

Записанное решение не остаётся в стороне: оно читается у исчерпанного run и
попадает в recovery- и repair-контекст преемника. Переход, которому нужен
отдельный маршрут — закрытие попытки, пересмотр плана, изменение критерия, —
останавливает продолжение и называет маршрут вместо подмены обычным ремонтом, и
не расходует выданный слот. Решение `re-review` повторяет ревью неизменённого
payload: runner детерминированно восстанавливает наблюдаемый scope и pre-review
floor, а при неудаче идёт обычный ремонт.

Изменение формулировки критерия — отдельное операторское решение с сохранением
прежней формулировки, автора и времени; сама запись формулировку не применяет,
применение идёт обычным маршрутом принятия, и до этого доставка не продолжается.
Автоматического продолжения без решения оператора нет; диагностика не выдаёт
себе ни слота, ни Acceptance, ни scope.

**Ограничение.** Маршрута технического восстановления среди переходов исчерпания
нет: существующее техническое восстановление принимает только исходный
остановленный run до первого ревью и линию, прошедшую ревью, выполнить не может.
Класс `infrastructure` сообщает средовую причину и не даёт полномочий; расширение
технического восстановления на такие линии — отдельная доставка инструмента.

## Операторский +1 к бюджету ревью

Первые два независимых ревью автономны. Каждое последующее требует отдельного
решения оператора через preview/authorize `review-allow` при исчерпании остатка.
Разрешение связывает точную историю и единственного recovery successor; расход
наследуется без сброса. Scope, frozen identity, proofs и финальные gates сохранены.

## Надёжность и инструменты

- Устранены семь падений полного набора: изоляция binding, регрессия контекста
  ревью, гонки прерывания проверок и объявленная совместимость.
- Повторные запуски OpenSpec CLI убраны из прогона: версия и readonly-вызовы
  мемоизированы по байтовой идентичности, из-за чего полный набор перестал
  тратить минуты на сотни одинаковых spawn'ов.
- Release-проверка больше не блокируется ложным требованием git-атрибутов, а
  лимит транзакции поднят под реальный размер кандидата.
- Тестовый harness больше не забивает `/tmp`: pytest держит только упавший
  прогон, а conftest возвращает права на запись в конце сессии, потому что
  снимок движка по-настоящему неизменяем (`0555`/`0444`).

## Дистрибутив и проверка

Состав runtime payload и правила исключений не менялись: `tools/openspec/.gitignore`
не входит в архив, исключения зависимостей задаёт потребитель. Новые модули ядра
(`scripts/changerail/exhaustion_diagnosis.py`) входят в runtime, тесты и board
остаются в исходном репозитории.

Локально проверены затронутые регрессии, полный набор, Ruff, `git diff --check`,
публичный скан и валидность OpenSpec; эти notes не заявляют выполненный CI или
реальную активацию. Полный CI точного release commit на Python 3.11 и 3.12
остаётся обязательным этапом публикации.

Архив `changerail-2.0.0-rc.6-runtime.tar.gz` для публикации собирают заново из
проверенного CI commit. Рядом публикуют `SHA256SUMS` и `release-provenance.json`
с точными source commit/tree и hash архива. Исторический
`distribution.json.provenance.upstream_commit` сохраняет прежнее значение.
[Quickstart](../quickstart.md) описывает проверку assets перед установкой.

Linux — текущая платформа. Совместимость прежних runtime и frozen runs сохраняется:
изменение identity исполнения не покрывается Python repair, поэтому переход на
этот кандидат действует только для будущих запусков и не даёт старым engines
права resume при изменённой identity.
