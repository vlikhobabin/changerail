# Исправление общего кода во время разработки

В режиме `shared-source` новый вызов ChangeRail использует текущие файлы общего
репозитория. Уже запущенный процесс продолжает работать с загруженным кодом.
Перед изменением инструмента остановите его runner; не меняйте общий исходник
при работающей доставке в любом подключённом проекте.

Обычный `resume` проверяет замороженную идентичность кода. Для ограниченного
продолжения после исправления Python-ядра доступны два явных действия:

Команды ниже выполняются из корня checkout ChangeRail. Явный `--project` выбирает
потребителя; относительные пути run и proposal считаются от его корня, а `--test`
обозначает существующую регрессию в общем исходнике.

```bash
./bin/chrl --project /opt/example-project runtime-repair-prepare .runtime/changerail/runs/REPLACE_WITH_RUN_ID \
  --reason 'Исправлена причина остановки реализации' \
  --test tools/changerail/tests/test_regression.py::test_reproduced_failure
./bin/chrl --project /opt/example-project runtime-repair-apply .runtime/changerail/runs/REPLACE_WITH_RUN_ID \
  --proposal .runtime/changerail/runs/REPLACE_WITH_RUN_ID/runtime-repairs/REPLACE_WITH_REPAIR_ID/proposal.json
./bin/chrl --project /opt/example-project resume .runtime/changerail/runs/REPLACE_WITH_RUN_ID
```

Подставьте путь proposal, возвращённый `prepare`, вместо `REPLACE_WITH_REPAIR_ID`.
Диагностика остановки и остальные способы продолжения описаны в
[руководстве оператора](operations.md).

`prepare` сам запускает выбранные pytest-проверки в общем репозитории, сохраняет
лог, исходники и их хеши. Код возврата должен быть нулевым, а pytest должен
подтвердить хотя бы одну прошедшую проверку. Переданные извне результаты и
утверждение `true` не заменяют этот запуск. `apply` повторно проверяет неизменность
исходника, сохранённых результатов и продуктовых изменений, затем добавляет
квитанцию в цепочку `runtime-repairs/applied/`. Оба действия удерживают блокировку
проекта; второй работающий runner исключает их выполнение.

Поддерживаемая граница намеренно ограничена: остановленный **первичный новый
native-запуск с явно подключённым общим исходником**, сохранённым точным
продуктовым payload и заполненным `finished_at`, **до первого завершённого
Change checkpoint и до записи evidence**. После исправления обычный `resume`
проходит все прежние проверки владения, плана, payload и исполнения.

Продолжение отклоняется, если:

- запуск исторический, установлен из локального комплекта или уже имеет
  `recovery_of`;
- завершён хотя бы один Change checkpoint, записано evidence или handoff;
- началось ревью, archive, preverification, финальная проверка или публикация;
- изменились профиль, launcher, адаптер проекта, схема или skill: этот механизм
  допускает только Python-файлы `scripts/changerail/`;
- продуктовый payload или результаты проверки изменились после подготовки.

Завершённый checkpoint пока нельзя сохранять через этот механизм: исправление
самого валидатора может сделать прежнее подтверждение недостаточным. Автоматического
аннулирования и повторной проверки таких доказательств здесь нет. Это ограничение
нужно учитывать при планировании ремонта на позднем этапе.

Исходный `run.json`, идентичность запуска, его тайминги, счётчики и evidence не
перезаписываются. Применённая квитанция уточняет разрешённую идентичность кода;
она не добавляет ревью, не перезапускает остановленный floor и не разрешает
публикацию. Исправление общего инструмента остаётся немеренным вмешательством,
отдельным от продуктового изменения.

В идентичность исполнения входят также `scripts/__init__.py`, загрузчик workflow
OpenSpec, проверка его установки, `package.json`, lockfile и bootstrap.
Изменение, добавление или удаление этих файлов блокирует обычный `resume`, в том
числе через общий исходник. Python repair не разрешает заменять этот контур.
Старые записи с неполной идентичностью не дополняются автоматически: совпадение
версии кандидата не доказывает совместимость сохранённого процесса.
